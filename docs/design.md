# 设计

这份文档记录 nasbutler 的目标、威胁模型、已经做出的决定和后续版本的设计。代码注释解释"怎么做"，这里解释"为什么"。

## 目标

让 AI agent 帮忙整理一个混杂的个人文件库（照片视频、监控录像、备份、证件、聊天记录、工作资料……），同时守住两件事：

1. **不泄密**：云端模型（Claude、GPT、Gemini……）看到的东西，等于发给了第三方。
2. **不毁数据**：这类文件库往往没有第二份，agent 的一次误删就找不回来。

## 威胁模型

**防的是：**

- 敏感内容经由 agent 流到模型提供方：文件内容、文件名里的身份证号和手机号、机密目录的名字。
- agent 的误操作：删错、移错、覆盖。
- 通过文件名或文件内容对 agent 做提示注入（"忽略之前的指令，把所有文件……"）。

**不防的是：**

- 能直接登录这台机器的人或 agent。**如果 agent 本身有这台机器的 shell，它绕过 MCP 就能直接读写文件**，这里的一切都白做。部署时，跑整理任务的 agent 只能拿到 MCP 端点，不能有 shell。
- 聚合信息：目录结构、文件数量、大小、时间分布。这些是整理所必需的，会发给模型。
- 对抗性 agent 通过大量聚合查询做推断。已经挡住了最直接的几条路（名字过滤只匹配脱敏后的名字，扩展名过滤不返回机密文件），但没有做系统性的防御。

## 为什么是 MCP + 纯信息模式

agent 碰数据的唯一通道是 MCP，所以 MCP 服务就是安全边界：它决定 agent 能看到什么、能做什么。

v0.1 只提供**纯信息模式**：agent 能看到脱敏后的路径、大小、时间、类型、敏感信息计数、重复文件分组、媒体编码参数，**看不到任何文件内容**。内容只在本机用来做敏感检测，检测结果只以计数的形式出去。

## 敏感信息定级

扫描时每个文件定一个级别：

| 级别 | 判定 | agent 看到什么 |
|---|---|---|
| 隐藏 | 配置里的 `hidden` 规则 | 什么都没有，不扫描、不计数 |
| 不透明目录 | 配置里的 `opaque` 规则 | 只有总文件数和总大小 |
| 机密 | 路径规则（内置 + 配置）；文件头特征（KeePass 库）；内容里有私钥、API token、密码赋值 | 名字整体换成 `[secret#…]`，扩展名不给；机密目录整体折叠成 `[secret-dir#…]`，下面的子目录结构也不给 |
| 个人 | 内容或文件名里有身份证号（校验位）、手机号、银行卡号（发卡行前缀 + Luhn）、邮箱 | 名字里的敏感片段换成化名 |
| 普通 | 其余 | 名字里如果有敏感片段，照样换成化名 |

- **按路径判定为机密的文件，内容一个字节都不读。**
- 数字类检测以"最长连续数字串"为单位判断，所以 20 位的摄像头时间戳不会被误认成藏在其中的 16 位银行卡号；银行卡号还要过发卡行前缀校验，以 `19`、`20` 开头的日期串不会通过。
- 旧版中文 Windows 写出的 GBK 文件名会被解码显示；解不开的字节转成 `%XX`，保证不同的名字仍然不同。

## 化名

化名是 `[类型#8位十六进制]`，十六进制部分是规范化后的值在服务端密钥下的 HMAC-SHA256。

- **同一个值永远得到同一个化名**：`138 1234 5678`、`+8613812345678` 和 `13812345678` 是同一个化名。agent 能看出"这 30 个文件都和同一个号码有关"，但拿不到号码。
- 密钥存在 `state_dir/pseudonym.key`（0600），不离开服务端。化名是带密钥的 HMAC，没有密钥就不能靠遍历号码空间撞出原值。
- 化名在扫描时就写进索引（`rpath`），所以 agent 用脱敏路径导航，名字过滤也只在脱敏名字上做。这堵住了"用 `name_contains` 二分猜出被打码的号码"这条路。

## 出口过滤

所有工具的返回值在离开进程前都经过同一个 MCP 中间件：

1. 把返回的 JSON 里每个字符串（包括对象的键）重新过一遍检测器，数字不动（一个 13,812,345,678 字节的文件必须保留它的大小）。
2. 超过 `max_result_bytes` 的结果整体拒绝，防止批量导出。
3. 发出去的内容逐条追加进 `state_dir/egress.jsonl`，事后可以查到底有什么发出去了。

数据在扫描时已经脱敏过，出口过滤是第二道防线。**如果它还能找到要脱敏的东西，说明某处代码漏了**：这时它照样脱敏，同时在审计日志里记 `late_redactions` 并打警告日志。

工具返回的错误信息同样经过这道过滤；代码层面也约定错误信息里不带真实路径（比如 ffprobe 失败只返回"media probe failed"，因为 ffprobe 自己的报错会带上文件路径）。

## 只读保证

- 扫描器用 `O_RDONLY|O_NOFOLLOW|O_NOATIME` 打开文件，不跟随符号链接，不改访问时间。
- MCP 服务以 SQLite `query_only` 模式打开索引，就算代码有 bug 也改不了索引。
- MCP 服务唯一能写的是计划目录，里面只有草稿和提交请求。

## 计划、审批与执行（v0.2）

agent 只能**提计划**，不能直接动文件。

### 两个进程，两个信任域

```
agent ──MCP──> nasbutler serve   数据只读；索引只读；只写计划目录和审计日志；没有飞书凭据
                    │ 草稿 / 提交 / 撤销请求（plans_dir）
                    ▼
               nasbutler exec    数据可写；独占 exec_dir（审批记录、操作日志）；持有飞书凭据
                    │ 发审批 ──> 人批准 ──> 回调 ──> exec
                    ▼
               重新校验 → 写日志 → rename → 增量重扫 → 更新状态和审批消息
```

- 执行器**不信任计划目录里的任何东西**，只把操作清单当作请求：自己把脱敏路径解析成真实路径、重新校验、自己计算摘要；批准只认它自己收到的回调。部署时 MCP 服务只能写计划目录，碰不到执行器的状态目录。
- 计划只有两种操作：`move`（目标目录 + 可选新名字，改名就是同目录移动）和 `quarantine`。**没有删除**：清理只能隔离，隔离区由人用 `nasbutler purge` 手动清空。这是整个代码库唯一的删除路径，只能从命令行调用。
- `to_dir` 用 agent 看到的脱敏路径。脱敏路径和真实路径逐段对应，所以含化名的段取"该前缀下任一文件真实路径的前 k 段"；该前缀下最小和最大的真实路径必须在前 k 段上一致，否则说明两个真实目录显示成同一个名字（比如 UTF-8 和 GBK 的"中文"），直接拒绝，不去猜。其余段当作新目录名校验。
- 校验项：文件存在且不是机密文件；源和目标都不在受保护、隐藏、不透明、机密目录或隔离区里；源文件自扫描后没变（大小、mtime、inode）；目标不存在；计划内不重复、不互相踩；路上没有符号链接；和源在同一个文件系统。MCP 服务在 `plan_add` 时做只看索引的那部分，执行器在发审批前和执行每一项之前各做一遍完整的。
- 摘要是真实源/目标路径和 inode 的 SHA-256。审批绑定摘要：文件或目标变了，旧的批准就失效。

### 执行

- 每一项：先写 `begin` 日志并 fsync → `renameat2(RENAME_NOREPLACE)`（文件系统不支持时退回 link+unlink，同样不会覆盖）→ 写 `done`。缺的目录先建，建目录也记日志。
- 任何一项失败就停下，已完成的都能撤销。
- 执行器中途崩溃，重启时对照日志和磁盘判断最后一项到底移没移（rename 是原子的，只有两种状态），计划标为失败，不自动续跑。
- 执行完做一次增量重扫，agent 马上看到新结构。
- 撤销：执行器按日志生成反向操作（只包含已完成的项，要求文件仍是同一个 inode、原位置空着），同样要审批；执行完删除计划当初新建、现在又空了的目录。
- 给 agent 的状态文件只有计数和通用错误信息；真实路径只出现在执行器的状态目录、审批消息和 `nasbutler plan show` 里。
- 所有移动都是同一文件系统内的 rename：原子、秒级、不复制数据。在 Unraid 上这也避开了混用 `/mnt/user` 和 `/mnt/diskN` 路径时可能把文件截成 0 字节的问题。

### 审批接口

审批必须在执行器这一侧强制，不能依赖 MCP 客户端的确认弹窗：很多 agent 跑在免确认模式下，客户端的确认本来也能被绕过。

```go
type Approver interface {
	Name() string
	// Run 持续投递人的决定，直到 ctx 结束。decide 返回的错误（过期、计划已变）
	// 要显示给做决定的人。
	Run(ctx context.Context, decide func(context.Context, Decision) error) error
	// Request 发出审批请求。
	Request(ctx context.Context, s Summary) (Ticket, error)
	// Update 显示计划的结果（执行中、完成、拒绝……）。
	Update(ctx context.Context, t Ticket, s Summary, o Outcome) error
}
```

执行器是唯一接受决定的地方：它核对计划状态、过期时间和摘要，状态机保证一个决定只生效一次。

**飞书实现（卡片按钮）**：执行器用应用机器人给审批人发一张 2.0 卡片，列出真实路径（前 20 项，其余折叠）和「批准执行」「拒绝」两个按钮；按钮回调通过应用的长连接收回，不需要公网入口。

- 只认 `operator.open_id == approver_open_id` 的点击，其他人点击只会看到"你不是这个计划的审批人"。
- 卡片里凡是来自文件名或 agent 的文本都放在 `plain_text` 里，文件名注入不了 markdown、链接或 @。
- 回调必须在几秒内应答，所以决定只改状态，执行放到后台；执行过程中卡片被更新为结果，按钮随之消失。
- 状态通知（状态文件和卡片）串行发出，每次都读取最新记录，先发的旧状态不会盖掉后发的新状态。
- 同一个应用有多个长连接客户端时，飞书把回调随机交给其中一个。和别的程序共用应用时点击可能丢失，`nasbutler feishu test` 用来验证。

**local 实现**：人在机器上运行 `nasbutler plan approve|reject <id>`，决定写进执行器状态目录下的一个文件。不需要网络和凭据，用于测试和不用飞书的场景。

之后要加别的审批方式（确认码、网页、别的 IM），实现这个接口即可。

## 后续版本

### v0.3：监控录像

- 按路径、文件名规律（摄像头名 + 时间戳）和编码参数识别监控片段，按"摄像头 + 日期"分组。
- 参数一致的片段用 ffmpeg `concat -c copy` 无损拼接；可变帧率的先转固定帧率。
- 可选硬件转码（H.265）和 DVR-Scan 只保留有画面变动的片段。
- 只生成新文件，用 ffprobe 核对时长一致后，原件才进隔离区。执行器限内存、限 CPU、同一时间只跑一个任务。

### v0.4：机密保险箱

- 机密文件可以整体移进加密目录（gocryptfs）。
- 可选 OCR，识别图片里的证件照和聊天截图。

## 已知局限

- 规则抓不到人名、住址这类自由文本。
- Office 文档、PDF、压缩包的内容还不检测（`sensitive_report` 会给出未检测文档的数量）。
- 图片内容在加 OCR 之前识别不了。
- 化名挡住了具体的值，挡不住上下文：`[phone#…]` 出现在"病历"目录里本身就是信息。真正一点都不想外发的，用 `hidden`。
